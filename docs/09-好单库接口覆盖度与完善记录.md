## 二、覆盖度对比

### 2.1 项目原有实现（迁移前）

`KuService` 里混了三套体系：

| 体系 | 域名 | 用途 |
| --- | --- | --- |
| v3 统一接口 | `v3.api.haodanku.com` | 本地生活、口令解析增值类 |
| CMS 接口 | `api.cmspro.haodanku.com` | 抖音商品/详情/转链/分类 |
| v2 接口 | `v2.api.haodanku.com` | 凑单、活动分类 |

已实现的路径（约 15 个）：`rest`、`hv_ratesurl`、`hv_order_list`、`meituan_activity_list`、`meituan_ratesurl`、`elm_activity_list`、`elm_activity_ratesurl`、`elm_order_list`、`dy_life_share`、`dy_life_city`、`dy_order_list`、`jd_goods_search`、`category_list`、`make_order`、CMS 的 4 个。

### 2.2 文档包里的接口（51 个，按能力分组）

| 分类 | 数量 | 项目原覆盖 |
| --- | --- | --- |
| 商品接口 | 16 | 仅抖音（走 CMS，非文档路径） |
| 转链接口 | 8 | 仅抖音（CMS） |
| 订单接口 | 11 | 部分（elm / hv / dy life） |
| 本地生活 | 5 | 大部分 |
| 活动接口 | 4 | 0 |
| 口令与工具 | 7 | 仅 `/rest` 增值类 |
| 合计 | **51** | **约 15** |

**明显缺口**：快手全套、闲鱼全套、各平台订单拉取、京东/拼多多/唯品会统一商品接口、活动转链。

### 2.3 判断：哪些该补，哪些不该补

| 缺口 | 处理 | 理由 |
| --- | --- | --- |
| 快手 5 个 | ✅ 补 | 普通接口，实测全通，新平台 |
| 闲鱼 5 个 | ✅ 补 | 普通接口，实测列表通 |

| 增值类 `/rest` | ❌ 不动 | 仍在 `KuService`，功能正常 |

## 三、本次改动清单

### 3.1 配置（4 份 yml）

```yaml
# application-dev.yml（app / admin 各一份）
haodanku:
  key: <APIKEY>
  waimaiKey: <同一 APIKEY>
  vip:
    appId: <占位，增值类用，用户未提供>
    appSecret: <占位>

# application-prod.yml（app / admin 各一份）
haodanku:
  key: ${HAODANKU_KEY:}
  waimaiKey: ${HAODANKU_WAIMAI_KEY:}
```

### 3.2 新增 `KuOpenApiService.java`

`mshop-store/src/main/java/com/junchen/modules/tk/service/KuOpenApiService.java`

设计原则：**不动历史代码**，新建独立 Service 承载官方文档定义的 v3 统一接口。

| 组成 | 说明 |
| --- | --- |
| 通用入口 | `get(path, params)` / `postForm(path, params)`，自动注入 `apikey`、自动跳过 null |
| 路径常量 | 51 个接口全部登记为常量，按商品/转链/订单/本地生活分组 |
| 高频方法 | 快手列表/详情/转链/口令、闲鱼列表/详情/转链、抖音口令、订单拉取通用方法 |
| 成功判断 | `isSuccess()` 统一认 `code == 1 \|\| code == 200` |
| 安全 | 日志打印参数时把 `apikey` 打码；异常返回结构化错误而非抛栈 |

**为什么不写 51 个语义方法**：项目里淘宝/拼多多/唯品会商品已有大淘客通道，重复封装没有收益。通用入口 + 常量足以覆盖所有接口，后续要用哪个直接调。

### 3.3 修复 `KuService` 两处成功码漏判

官方文档明确：

> 接口返回的 `code` 为 `1` 或 `200` 表示成功，其他 `code` 一律按失败处理。

原代码：

```java
if (codeVO.getCode() == 200) { ... }                    // line 155，漏了 1
if (body == null || (!code.equals(0) && !code.equals(200))) // line 548，漏了 1
```

已改为同时接受 `1` / `200`（第二处额外保留 `0`，兼容 CMS 返回）。

**这个 bug 是实测撞出来的**：`supersearch` 和 `column` 都返回 `code=1`，原代码会把成功响应当失败丢掉。

## 四、实测结果（真实调用，非推测）

| 接口 | code | 结论 |
| --- | --- | --- |
| `ks_item_list` 快手商品列表 | 200 | ✅ 返回真实快手商品 |
| `ks_item_detail` 快手详情 | 200 | ✅ |
| `ks_item_ratesurl` 快手转链 | 200 | ✅ 返回推广链接 |
| `idle_goods_query` 闲鱼商品列表 | 200 | ✅ |
| `column` 淘宝商品列表（`back=5`） | **1** | ✅ 证明 code=1 是成功 |
| `supersearch` 淘宝搜索「抽纸」 | **1** | ✅ 同上 |

## 五、修正之前的结论

此前做过一次平台盘点，结论是「项目不支持快手」——依据是代码里搜不到任何快手相关实现。这个判断当时没错，但**只覆盖了项目自身，没算上聚合服务商能提供的通道**。

**现在修正**：好单库提供了完整的快手通道（商品列表/详情/转链/口令/订单），且实测全部返回成功，属于「能通过聚合接入」，不该归为「不支持」。

| 平台 | 修正后状态 |
| --- | --- |
| 快手 | ✅ 可接入（好单库普通接口，商品/详情/转链/口令/订单都有） |
| 闲鱼 | ✅ 可接入（好单库普通接口） |
| 小红书 | ❌ 仍无公开 CPS API |

同理，`00-上线前总检查表.md` 等文档里若提到「不支持快手」，以本文为准。

## 六、权限边界（文档包明确）

| 平台/能力 | 权限要求 |
| --- | --- |
| 普通接口（apikey） | 淘宝商品、快手全套、闲鱼、部分本地生活 |
| 增值类（appkey + appsecret + sign） | 淘口令解析、粘贴板识别、短链、CMS 链接 |
| 需单独申请 | 京东、拼多多、唯品会、抖音、闲鱼订单 |
| 需人工开通 | 美团、淘宝闪购、本地生活特权、官方账号授权 |
| 订单类 | 通常比商品类更严格，需单独确认 |

项目当前 `haodanku.vip.appId/appSecret` 仍是占位符，**增值类接口（`/rest`）暂时用不了**。但 `KuService` 里 `/rest` 的实现用的是 `haodanku.key` 做 MD5 签名，属于历史做法，能否继续用需实测确认。

## 七、后续建议

1. **APP 端接入快手/闲鱼**：Service 层已就绪，还缺商品列表页、详情页、订单归因。要不要做，看业务价值。
2. **订单冗余**：把 `KuOpenApiService.orderList()` 接进定时任务，与大淘客订单做交叉校验，避免单点。
3. **抖音权限**：如要切 v3 统一接口，需联系好单库管理员开通；现有 CMS 通道可继续用。
4. **增值类密钥**：如需 `/rest` 稳定可用，去好单库创建增值应用拿 appId/appSecret 并填 `haodanku.vip.*`。
5. **凭据安全**：dev 两份 yml 被 git 跟踪，APIKEY 会随 commit 进仓库，push 前处理。
