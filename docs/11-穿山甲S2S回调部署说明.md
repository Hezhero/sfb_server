# 穿山甲激励视频 S2S 回调部署说明

> 对应工单 10。S2S（Server-to-Server）回调是积分防伪的第二道闸门，
> 与客户端上报配合形成两阶段校验。

---

## 一、为什么需要 S2S

当前 `/csj/reward` 的 `transactionId` 由 APP 客户端自己生成（`csj_${时间戳}_${6位hex}`）。
被 hook 的客户端可以伪造任意 `transactionId` 无限领积分——这是**真实可被薅羊毛的漏洞**。

S2S 的作用：用户看完广告后，由**穿山甲服务端**主动回调我方，验签通过后把 `trans_id`
落库为「可发放」。客户端上报奖励时，服务端比对白名单，两层都过才发积分。

> 官方明确说明 S2S 只是「透传验证」（开发者返回 true/false，最终由客户端
> `onRewardArrived` 感知结果）。**单靠 S2S 不能防伪造，必须两层校验**——
> 本实现已按此设计。

---

## 二、需要在穿山甲后台配置

1. 进入穿山甲媒体平台 → 找到激励视频代码位 → 编辑 → 开启「服务端激励回调」。
2. 回调地址填写：

   ```
   https://<你的域名>/csj/s2s-callback
   ```

   ⚠️ **必须使用域名，不能用 IP**——官方说明穿山甲部分机房无法正常访问 IP 形式的 URL，
   会导致收不到回调。同时建议使用 HTTPS。

3. 记下该应用/代码位对应的 **app security key**（回调验签用）。
   ⚠️ 这与电商联盟 `csj-ecom.secureKey` 是**不同凭证**，不要混用。

---

## 三、需要在本服务配置

在 `application-{dev,prod}.yml` 中配置（**不要提交明文**）：

```yaml
csj:
  s2s-security-key: ${CSJ_S2S_SECURITY_KEY:}   # 穿山甲广告变现的 app security key
```

本地调试：

```bash
export CSJ_S2S_SECURITY_KEY=<穿山甲后台的 security key>
```

**未配置该值时不启用 S2S 校验**，发奖走原来的三层防刷逻辑（向后兼容历史部署）。
配置后才强制两阶段校验。

---

## 四、官方回调协议（已核实 supportcenter/5416）

- 穿山甲以 **GET** 请求回调地址，回传：
  `user_id` / `trans_id` / `reward_name` / `reward_amount` / `extra` / `sign`
- 验签：`sign = sha256(SecurityKey + ":" + trans_id)`
- 我方返回 JSON：`{"isValid": true}`（字段名必须是 `isValid`，不是 GroMore 版的 `is_verify`）

---

## 五、数据库

S2S 白名单表：`docs/sql/mw_csj_s2s_whitelist.sql`，部署前需执行。

- 验签通过 → 插入一条 `consumed=0` 的白名单记录（trans_id 唯一）
- 重复回调（上游重试）→ 幂等返回 isValid=true，不重复插入
- 发奖成功 → 标记 `consumed=1`

---

## 六、验收要点

- [ ] 回调地址用域名（非 IP），HTTPS
- [ ] 后台已开启「服务端激励回调」
- [ ] `CSJ_S2S_SECURITY_KEY` 已注入且为广告变现 security key（非电商联盟 secureKey）
- [ ] `mw_csj_s2s_whitelist` 表已建
- [ ] 用穿山甲后台的「回调测试」功能验证：返回 `{"isValid":true}`
- [ ] 伪造 transactionId 上报 `/csj/reward` 被拒绝（返回"奖励验证未通过"）
