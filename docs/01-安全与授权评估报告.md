## 一、结论摘要

**没有发现恶意后门。** 全量源码中不存在命令执行、反序列化加载、隐藏账号、向作者服务器回传业务数据、远程开关等典型后门手法。

**但存在 6 类"等同后门"的高危默认配置**：签名密钥、加密密钥、支付/联盟推广位全部以明文固定值写在仓库里。不修改就上线，等于把鉴权、数据、佣金三样东西同时交出去。这些不是作者故意留的陷门，而是"开源模板默认值"的通病——但后果与后门一致。

| 等级 | 问题 | 后果 |
| --- | --- | --- |
| **P0** | APP 端 JWT 密钥硬编码 `mshopmini` | 任何人可伪造任意用户身份，完整接管账号 |
| **P0** | 淘客推广位 PID 为作者所有 | 佣金进入原作者账户，你白干 |
| **P0** | Druid 监控台 `admin/123456` + 免登录放行 | 数据库 SQL 监控、连接信息暴露 |
| **P1** | 管理端 JWT `HS512` 密钥硬编码 | 可伪造管理员令牌 |
| **P1** | RSA 私钥 / AES 密钥硬编码 | 登录密码与敏感字段加密形同虚设 |
| **P1** | CORS `*` + `allowCredentials=true` | 任意站点可携带用户凭证发起请求 |
| **P2** | sm.ms 图床 token 硬编码（作者账号） | 上传图片进他人图床，随作者账号失效 |

**授权方面有两个必须处理的问题**：项目自身的 LICENSE 与 README 存在表述冲突（自用商用是否收费）；依赖里混入了 **AGPL 的 iText 5** 和 **商业闭源的 Aspose.Words**，这两个才是真正的"商用授权地雷"。

> **状态更新（2026-10-30）**：iText 已替换为 **OpenPDF 1.3.43**（LGPL/MPL），AGPL 约束解除。详见 4.2 节。

## 三、高危问题清单（含文件与行号）

### P0-1 APP 端 JWT 密钥硬编码，可伪造任意用户

**位置**：`mshop-app/src/main/resources/config/application-prod.yml:68`（dev 同）

```yaml
mshop:
  security:
    jwt-key: mshopmini      # ← 明文固定值，随开源仓库公开
```

**利用链**：`JwtToken.java:82` 用该密钥 `HMAC256` 签发，载荷只有 `uid / scope / uName`；`UserInterceptor.java:66-82` 验签通过后直接 `userService.getById(uid)` 建立登录态，**没有任何来源校验、设备绑定或 token 版本号**。

任何人拿到源码即可用 `mshopmini` 签一个 `uid=1` 的 token，直接以该用户身份调用全部 APP 接口（查看订单、提现、改收货地址）。

**修复**：改为 32 位以上随机串，且通过环境变量注入，不进仓库。

```yaml
mshop:
  security:
    jwt-key: ${MSHOP_JWT_KEY}
```

```bash
# 生成
openssl rand -base64 48
```

> 改完后所有已签发 token 立即失效，属于预期行为。

### P0-2 淘客推广位 PID 全部是作者的

**位置**：
- `mshop-admin/.../application-prod.yml:150,152`
- `mshop-app/.../application-prod.yml:141,143`

```yaml
tb:
  pid:
    channelPid: mm_52650383_39582271_114587650437   # 作者渠道 PID
    tljPid:     mm_52650383_3088500089_115682150104 # 作者淘礼金 PID
```

同时 `pdd.pid: 1784892_252288888` 也是固定值。

**后果**：所有转链订单的佣金结算到该 PID 对应账户。这不是技术后门，但业务上是**直接的资金损失**，且订单采集会按 `adZoneIds` 过滤，别人的 PID 订单你不会采到——系统看起来"没订单"，钱进了别人口袋。

**修复**：换成自己在各联盟后台申请的 PID，并同步 `adZoneIds` 白名单（`TbConfig.getAdZoneIds()`）。

### P0-3 Druid 监控台弱口令且免鉴权放行

**位置**：
- `mshop-admin/.../application-prod.yml:40-41` → `login-username: admin` / `login-password: 123456`
- `mshop-admin/.../security/config/SecurityConfig.java:123` → `.antMatchers("/druid/**").permitAll()`

**后果**：`http://host:8001/admin/druid/` 直接暴露 SQL 监控、慢查询、Session、URI 统计；默认口令进得去。

**修复**：改强口令 + 配 IP 白名单（`statViewServlet.allow`），生产建议直接 `enabled: false`。

### P1-1 管理端 JWT 密钥硬编码

**位置**：`mshop-admin/.../application-prod.yml:70,72`

```yaml
jwt:
  secret: k09BQnaF                        # 7 字符，严重偏弱
  base64-secret: ZmQ0ZGI5NjQ0MDQwY2I4MjMxY2Y3ZmI3MjdhN2ZmMjNhODViOTg1ZGE0NTBjMGM4NDA5NzYxMjdjOWMwYWRmZTBlZjlhNGY3ZTg4Y2U3YTE1ODVkZDU5Y2Y3OGYwZWE1NzUzNWQ2YjFjZDc0NGMxZWU2MmQ3MjY1NzJmNTE0MzI=
```

`TokenProvider.java:53,68` 用 `base64-secret` 做 HS512 签名。密钥公开 → 可伪造管理员令牌。注意 `jwt.secret` 实际未被 `TokenProvider` 使用（遗留字段），真正生效的是 `base64-secret`。

**修复**：重新生成 ≥88 位 Base64 随机串，环境变量注入。

### P1-2 RSA 私钥与 AES 密钥硬编码

**位置**：`mshop-admin/.../application.yml:46`（`rsa.private_key`）、`:49`（`aes.encryptKey`）
`mshop-app/.../application.yml` 同。

RSA 用于登录密码传输解密，AES 用于敏感字段加解密。密钥公开意味着抓包即可解出明文密码、库中加密字段可离线解密。

**修复**：成对重新生成 RSA 密钥（前端公钥需同步替换），AES 密钥换新。**换 AES 密钥会导致存量密文无法解密**，需评估迁移方案或保留旧密钥做兼容解密。

### P1-3 CORS 配置过于宽松

**位置**：`mshop-admin/src/main/java/com/junchen/config/ConfigurerAdapter.java:41-43`

```java
config.setAllowCredentials(true);
config.addAllowedOriginPattern("*");
```

允许任意源携带 Cookie 发起跨域请求，配合管理后台的 Cookie/Session 机制可被 CSRF 利用。

**修复**：收敛为管理后台实际域名白名单。

## 四、商用授权分析

### 4.1 项目自身授权：LICENSE 与 README 存在冲突

这是最需要先厘清的一点，两份文件说法不一致：

| 出处 | 原文 | 含义 |
| --- | --- | --- |
| `LICENSE` 2.1 | 「以自用为目的，您可将本软件用于盈利或非盈利项目上，**且不受任何限制**」 | 自用可盈利、免费 |
| `LICENSE` 2.2 | 「以自用为目的，在**保留版权标识**的前提下您可任意修改程序源码」 | 可改，但留标识 |
| `LICENSE` 2.5 | 「未经我们书面许可，**不得删除网站底部及相应的官方链接**」 | 禁止去标识 |
| `README` | 「**商用必须保留版权信息，并支付商用授权费用**」 | 商用要付费 |
| `README` | 「禁止将本项目的代码与资源进行任何形式的出售」 | 禁止转售 |

**如何理解**：法律上以 `LICENSE` 正文为准（它是正式许可协议，README 是说明文档）。`LICENSE` 的关键限定词是「**以自用为目的**」。因此存在一条清晰的分界线：

| 场景 | 是否属于"自用" | 结论 |
| --- | --- | --- |
| 自己公司运营一套淘客 App 赚钱 | ✅ 是 | **LICENSE 2.1 明确允许，无需付费** |
| 改源码做自己品牌的 App | ✅ 是 | 允许，但须保留版权标识（2.2/2.5） |
| 给客户做一套、交付源码或安装包 | ❌ 否 | 超出"自用"，需商业授权 |
| 做成 SaaS 多租户卖给多个商家 | ❌ 否 | 超出"自用"，需商业授权 |
| 把源码/安装包挂出去卖 | ❌ 否 | 2.2 明令禁止 |
| 去掉页脚版权、官方链接 | ❌ 违规 | 违反 2.5，构成侵权 |

**结论**：如果你是自己运营（哪怕盈利），**按 LICENSE 不需要买授权**，只要保留版权标识。真正需要付费的是"对外交付/多租户分销"这类行为。

### 4.3 关于"规避商用授权"的正确做法

必须区分两件事：**规避不必要的技术依赖**（合法、推荐）和 **规避应付的授权费**（违法、不可取）。

**可以做的（合法降本）**：

1. **不启用 Aspose**：`shop.convertContract: false`（默认值），电子合同功能整条链路不参与运行，就不产生 Aspose 授权义务。
2. **用 OpenPDF 替换 iText**：这是消除 AGPL 传染的标准做法。全仓库仅 `WordUtil.java` 引用 iText 的 4 个类（`Image` / `Rectangle` / `PdfReader` / `PdfStamper`），换成 OpenPDF 后包名从 `com.itextpdf` 改为 `com.lowagie`，API 一致。**已于 2026-10-30 完成**：仅改 `mshop-system/pom.xml` 依赖坐标与 4 行 import，编译通过、盖章功能实测通过。
3. **走"自用"路径**：自己运营、保留版权标识，符合 LICENSE 2.1，不产生迈沃授权费。
4. **把付费点砍掉**：商业版独有的多租户、在线打包、价保监控等能力，本仓库本来就没有，不需要"破解"，直接不宣传即可。

**不能做的（会踩法律红线，本报告不提供方案）**：

- 删除或隐藏页脚版权、官方链接（违反 LICENSE 2.5，构成著作权侵权）。
- 破解商业版授权机制（违反 LICENSE 2.3）。
- 转售源码或安装包（违反 LICENSE 2.2）。
- 继续使用作者的淘客 PID、AppKey、短信签名（这不是授权问题，是**盗用他人账号资源**，且资金流向他人）。

**如果确实要做对外交付业务**，合规路径只有三条：向迈沃购买对应商业授权；基于 RuoYi / Mall 等 Apache 2.0 项目自研；采购其他明确允许分发的商业授权产品。

这套代码的工程质量中上（分层清晰、订单采集考虑了幂等与分页、部分地方有安全修复痕迹，如 JDK 17 兼容、`siteId` 过滤、拼多多游标翻页修复），**没有发现恶意代码**。

它的问题集中在"开源模板默认值"：密钥、PID、第三方凭据全是作者的明文值。这类问题的特点是——**不改能跑，跑起来就是在给别人打工**。P0 四项必须在首次启动前改完，改完这套系统才真正属于你。

授权上真正要花钱的地方不是迈沃，而是 iText（AGPL）和 Aspose（商业库）。前者**已替换为 OpenPDF，AGPL 约束解除**；后者建议不启用。项目自身按 LICENSE 2.1 自用模式运营，不需要额外付费，但版权标识必须保留。
